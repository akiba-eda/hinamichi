## 0. 一言ピッチ

**「災害速報が来た瞬間、あなたが開く前に、AIが"あなたに関係あるか"を判断し、逃げるべきなら避難先と経路を決め、家族にあなたの状態を伝え続ける」**

人が握っていた「速報を見て、自分事か判断し、どこへ逃げるか決め、家族に連絡する」という入り口を、AIエージェントに渡す。

## 1. 審査5基準への回答(設計の北極星)

| 基準 | 回答 | 実装で見せるもの |
|---|---|---|
| ①セキュリティ | 生座標・氏名を LLM に渡さない(データ最小化)。APIキーはサーバー側のみ。他人に影響する操作は承認ゲート | Agent Log 画面で「LLM に渡した入力」を表示(座標が無い) / 承認カード UI |
| ②コスパ | 一次判定=小型モデル、避難先選定のみ上位モデル、経路再計算は LLM 不使用。待機中 0 円 | OrcaRouter Request Logs / アプリ内「今回のインシデントのコスト」表示 |
| ③信頼性・堅牢性 | LLM 出力を安全ルールで検証 → 不合格・失敗・タイムアウト時はルールベース選定にフォールバック。プロバイダ障害は OrcaRouter フェイルオーバー | デモで LLM 応答を意図的に壊す/遅延させ、案内が止まらないことを実演 |
| ④自律性 | 速報→関連判定→起動判断→ツール選択→選定→通知→状況監視→再選定→終了判定まで人の操作なし | 通知を開いた時点で全部終わっている / 満員時に自動で次点へ切替 |
| ⑤独創性 | 「最寄り表示」でなく「災害種別×ハザード×混雑で選定」+「安否状態を AI が自動更新して共有」+「群制御で殺到回避」 | 地震/豪雨で行き先が変わる / フレンド画面のステータスがリアルタイムで進む |

**主催の注意「自律性が上がるほど①③の要求が跳ね上がる」への回答**: 自動実行できる操作と承認必須の操作を明確に分離(§6.4)。

## 2. ユーザーストーリー

### 平時
- U1: アプリを開くと現在地周辺のハザード(浸水・土砂・津波)と避難推奨場所が地図に出る。出先でも使える。
- U2: フレンドを登録し、災害時に自分の状態を自動共有することに同意する(相手ごと)。

### 災害時
- U3: アプリが閉じていても災害通知が届く(現在地に関係なく全ユーザーへ一斉)。
- U4: 通知を開く(またはバックグラウンドで)と現在地を取得し、AI が各種災害情報ツールを叩いて「自分に関係ある災害か」を判断する。
- U5: 避難が必要なら地図が展開し、避難場所が選定され、道案内が始まる。理由が表示される。
- U6: 同時に、自分の安否状態が「避難判断中→避難中→避難完了/安全地域」と自動更新され、同意済みフレンドへ共有される。
- U7: 移動中に避難所が満員・通行不能・新たな速報が来たら、AI が自動で再選定し、フレンドにも行き先変更が届く。
- U8: 避難完了(避難所到着 or 本人確認)でエージェントが停止し、記録が残る。

│ runAgent(callable)    → Agent Loop(下記)                    │

│ onIncidentUpdate      → フレンドへ状態共有 → FCM              │
│                                                             │
│  Agent Loop                                                 │
│   ├ Tools: alerts / hazard / shelters / crowd / route       │

│   ├ SafetyValidator(ハードルール)                             │
│   └ RuleBasedFallback                                        │
└──────────────────────────┬────────────────────────────────┘
                           │ OpenAI 互換
                     ┌──────────────┐

**なぜエージェントをサーバー側に置くか**
- OrcaRouter の鍵を端末に載せない(①)
- 端末が落ちても/通信が細くても、ループ状態が Firestore に残り復旧できる(③)
- Phase2 の「開かなくても動く」に自然に拡張できる(④)
- 混雑カウンタ・フレンド共有はサーバー側の一貫性が要る

## 5. データモデル(Firestore)

```
users/{uid}
  displayName, fcmToken, createdAt
  avatarImage, avatarMood                    # アイコン。画像は 256px の base64(Storage は使わない)
  consent: { shareStatusWithFriends: bool, shareShelterName: bool, shareLocationWithFriends: bool }
  lastKnownArea: { areaCode, updatedAt }     # 市区町村レベル。一覧・詳細ではこちらを読ませる

friends/{uid}/list/{friendUid}
  status: "pending"|"accepted", autoShare: bool
  shareLocation: bool                        # この相手に自分の位置を見せるか(既定 false)
  displayName, avatarImage, avatarMood       # 相手のアイコン(サーバーが写す)

locations/{uid}                              # 2026-09-20 追加。§5.1 を参照
  lat, lng, accuracyM, at, batteryPct, areaName

alerts/{alertId}
  type: "earthquake"|"heavy_rain"|"flood"|"tsunami"
  severity, areaCodes[], issuedAt, source: "simulator"|"jma", payload

incidents/{incidentId}                      # ユーザー×アラートの1回のエージェント実行
  uid, alertId, state: (§6.1 参照)
  relevance: { isRelevant, reason, model, costUsd }
  decision: { shouldEvacuate, disasterType, reason, model, costUsd }
  selectedShelter: { shelterId, name, walkMin, reasons[], validatedBy: "llm+rules"|"fallback" }
  rejectedCandidates: [{ shelterId, rule }]   # 安全ルールで弾いた候補(Agent Log 用)
  route: { polyline, distanceM, durationS }
  timeline: [{ at, event, detail }]
  cost: { totalUsd, calls: [{ step, model, tokens, usd }] }
  createdAt, closedAt

incidents/{incidentId}/agentLog/{seq}
  at, kind: "tool_call"|"tool_result"|"llm_request"|"llm_response"|"validator"|"fallback"|"action"|"approval"
  name, inputSummary (LLM に渡した抽象化入力そのもの), outputSummary, model, latencyMs, costUsd

statuses/{uid}                               # フレンドに見せる公開状態(最小限)
  state: "safe"|"assessing"|"evacuating"|"arrived"|"safe_zone"|"unknown"
  shelterName?: string(同意時のみ), updatedAt, incidentId

shelters/{shelterId}                         # デモ地域の数十件を同梱
  name, lat, lng, types: ["wide_area","tsunami","flood_ok","landslide_ok"]
  elevationM, floodDepthClass, capacity, address

shelters/{shelterId}/crowd (単一 doc)
  assigned: number, updatedAt

hazardCells/{geohash6}                       # 簡易ハザード格子
  flood: 0..3, landslide: bool, tsunami: bool

approvals/{approvalId}
  uid, incidentId, action: "send_free_text"|"share_raw_location", payload, status
```

**セキュリティルール要点**: `incidents`/`agentLog` は本人 read のみ、write は Functions のみ。`statuses` は accepted フレンドのみ read。`shelters/crowd` は Functions のみ write。`locations` は**本人と、本人が個別に許可したフレンドだけ** read(§5.1)。書き込みは全コレクションでサーバーのみ ── 他人の位置を偽装できないようにするため。

### 5.1 位置共有(2026-09-20 決定。当初案からの変更)

**当初は「生座標はどのコレクションにも保存しない(Functions のメモリ内でのみ使用)」としていた。これを撤回し、`locations/{uid}` に生座標を保存する。**

変更した理由は、この撤回でしか満たせない要求が出てきたため:
> 通信インフラが落ちても、**最後に位置が届いた場所**がわかれば家族は動ける。

市区町村レベル(`lastKnownArea`)では「市川市にいる」までしか言えず、捜索の役に立たない。

**LLM 側のデータ最小化(§6.3)は一切変えない。** 審査基準①の説明は「座標を持たない」から、目的ごとに線を引く形に言い直す:

| 渡す先 | 座標 | 根拠 |
|---|---|---|
| LLM(OrcaRouter 経由) | **渡さない** | §6.3 の抽象化。AgentLog で実物を見せられる |
| 家族・友人 | **本人が相手ごとに許可したときだけ** | `friends/{uid}/list/{friendUid}.shareLocation` + 元栓の `consent.shareLocationWithFriends` |
| それ以外 | 渡さない | ルールで read 不可 |

**歯止め**(実装済み):
- 既定は共有しない。元栓(全体)と相手ごとの許可の**二段**で、両方立っていないと read できない
- 元栓がオフの間は**位置を測りもしない**(ストリームを起動しない)
- 50m 動いたときだけ送る。一定間隔のポーリングはしない ── 災害時に電池を削らないため
- 見る側には**必ず観測時刻を添える**。古い位置を現在地と誤解した捜索が、この機能でいちばん危ない
- iOS のバックグラウンド位置インジケータを出す(`showBackgroundLocationIndicator`)。黙って測らない

**残るリスク**: 漏えい時の被害は「状態だけ」から「居場所」に上がる。ルールの読み取り条件が唯一の壁なので、`locations` のルールは変更時に必ずレビューすること。

### 5.2 合流(meetups) — 2026-09-22 追記

当初の設計書に書かないまま実装した。仕様が無いまま作ったので、人数も落ち合う場所も
選べない状態で止まっていた。**定義をここに置く。**

> 合流とは、「どこで・誰と落ち合うか」を参加者全員で共有する 1 つの約束。
> 全員が同じ地点の旗を見て、各自は自分がそこまで何分かかるかを見る。
> 平時は待ち合わせ、災害時は避難先での落ち合いとして、同じ仕組みが色と文言だけ変えて動く。

```
meetups/{meetupId}
  name        落ち合う場所の名前(避難所名 or 「◯◯さんのいる場所」)
  lat, lng    作成時に確定。以後動かない
  memberUids  作った本人を含む 2〜20 人。全員がこの doc を read できる
  ownerUid    作った人
  fromIncident 災害から作ったか。true なら色と文言が「避難先で合流」に変わる
  active      true の間だけ旗が出る
  createdAt / endedAt
```

**不変条件**
- 1人が同時に入る active な合流は **1つ**。新しく作ると前の合流からは自動で抜ける
  (画面が1件しか出せない以上、守らないと古い合流が新しいものを隠す)
- メンバーは friends が accepted の相手のみ(`assertFriend`)
- **地点は動かさない**。相手を追いかける作りにすると「相手の現在地を常時見る」ことになり、
  §5.1 の位置共有の原則と衝突する
- 落ち合う場所は**避難所一覧か相手の位置から選ぶ**。地図から任意の地点を立てさせない
  ── 浸水想定の中を選べてしまい、避難先を安全ルールで検算している意味が無くなる

**終わり方**: 「抜ける」= 押した人が memberUids から外れる。残り1人以下で `active:false`。
離脱と解散を分ける(1人の離脱で他のメンバーの旗まで消さない)。

### 5.3 よく行く場所(places) — 2026-09-22 追記

```
places/{uid}              inside: [placeId]   いま中にいる場所
places/{uid}/list/{id}    name / lat / lng / radiusM(既定150) / kind
placeEvents/{uid}/list/{id}  placeName / arrived / at
```

**出入りの判定はサーバーでやる。** 画面を開いていない・寝ている間の到着こそ知りたいので、
端末側で判定すると意味が無い(`tools/places.ts`)。

境界を跨ぐたびに通知が往復しないよう、**出るときの輪は入るときより広く取る**
(ヒステリシス 1.35 倍)。測位は数十m揺れるので、同じ半径で出入りを判定すると
家の中にいるだけで「着いた/出た」を繰り返す。

通知するのは**到着だけ**。出発まで鳴らすと多すぎて読まれなくなる。
相手に届くのは**場所の名前だけ**で、座標は送らない。

## 6. エージェント設計

### 6.1 状態遷移(incident.state)

```
IDLE
 └─(alert 受信 & 位置取得)→ ASSESSING_RELEVANCE
      ├─ 無関係 → CLOSED_NOT_RELEVANT      (ユーザーには「対象外」バナーのみ)
      └─ 関係あり → DECIDING
           ├─ 避難不要(屋内待機等) → MONITORING_STAY  ─(状況悪化)→ DECIDING
           └─ 避難必要 → SELECTING_SHELTER
                └→ GUIDING                            ★ status=evacuating
                    ├─(満員/通行不能/新速報)→ RESELECTING → GUIDING
                    ├─(避難所 100m 以内 or 本人タップ)→ ARRIVED   ★ status=arrived
                    └─(危険域外 & 本人タップ)→ SAFE_ZONE           ★ status=safe_zone
 ARRIVED / SAFE_ZONE → CLOSED
 任意の状態 →(LLM 失敗 3 回)→ FALLBACK_GUIDING(ルールベース)→ GUIDING と同等
```

**終了条件**(「いつ止めるか」): ARRIVED / SAFE_ZONE / NOT_RELEVANT / 本人が「終了」/ アラート解除。
**再評価トリガー**: crowd 変化(onSnapshot)、新 alert、位置が 200m 以上移動して経路逸脱、10 分タイマー。

### 6.2 ループ 1 周の処理(runAgent)

```
1. 位置取得(端末)→ Functions へ送る(HTTPS、保存しない)
2. Functions: 座標 → areaCode / geohash / 距離計算 用に一時利用
3. [LLM-小] 関連判定: 入力 = { alert 種別・震度/雨量, ユーザーの area 名, 屋内外推定 }  ※座標なし
4. ツール実行(決定的):
     hazard = getHazard(geohash)
     candidates = listShelters(areaCode, radius) → 各候補に walkMin / 種別 / hazard 判定 / crowd% を付与
5. [LLM-大] 選定: 入力 = { disasterType, hazardSummary, candidates(抽象特徴のみ, ID は仮名 A/B/C) }
     出力 = { choice: "B", shouldEvacuate, reasons[], confidence }
6. SafetyValidator(choice) → NG なら「NG 理由を添えて再選定 1 回」→ それも NG ならフォールバック
7. getRoute(from, shelter) (Directions API、LLM 不使用)
8. incident 更新 / statuses 更新 / agentLog 追記 / フレンドへ FCM
9. 監視モードへ(crowd・alert・位置の onSnapshot / タイマー)
```

**LLM をツール呼び出し主体にするか(Function Calling)、固定パイプラインにするか**
- 審査では「AI がツールを選んだ」ログが映える一方、tool calling は不安定・遅延の元。
- **採用**: ステップ 3 と 5 は tool calling を使う(LLM に `get_hazard` `list_shelters` `get_crowd` を公開し、自分で呼ばせる)。ただし Functions 側で**必ず呼ばれるべきツールは呼ばれていなくても補完**し、最終的に SafetyValidator を通す。ログには「LLM が選んだツール」と「システムが補完したツール」を区別して記録 → 自律性と堅牢性の両方を見せられる。
- 時間が無ければ固定パイプラインに落とし、ログ表示だけ残す(見た目は同じ)。

### 6.3 LLM 入力の抽象化(データ最小化の実装)

LLM に渡すもの / 渡さないもの:
| 渡す | 渡さない |
|---|---|
| 災害種別・規模 | 緯度経度 |
| 市区町村名(areaCode の表示名) | 住所・氏名・uid・fcmToken |
| 現在地のハザード判定(浸水クラス・土砂・津波) | 生のハザードポリゴン |
| 候補避難所: 仮名(A/B/C)・徒歩分・種別・ハザード判定・混雑% | 避難所名・座標(選定後にサーバーで復号) |
| 屋内/屋外・移動中の推定 | 移動履歴 |

→ プロバイダ側には「東京都渋谷区にいる誰かが、徒歩 8 分の広域避難場所 B を勧められた」以上は再構成できない。PII Shield は氏名・連絡先・自由文が混じった時の最終防波堤として有効化。

### 6.4 権限モデル(自律 × 安全)

| 操作 | 実行主体 | 条件 |
|---|---|---|
| 関連判定・避難要否・避難所選定・経路計算 | 自動 | 常に |
| 安否ステータス更新(assessing/arrived…) | 自動 | 常に(本人にも通知) |
| ナビ開始(status=evacuating + 行き先共有) | **承認 or タイムアウト** | 「このルートで行く」タップ、または 30 秒無応答で自動開始(フレンドには「応答なし」を明記) |
| フレンドへ状態+避難所名の共有 | 自動 | 事前同意 `autoShare` かつ `shareShelterName` |
| 混雑カウンタ加算(「向かう」宣言) | 自動 | 他人に影響するが人命優先で自動。ただし 1 ユーザー 1 枠、離脱で減算 |
| 自由文メッセージ送信 | **承認必須** | 承認カードで本人タップ |
| 生位置の共有 | **承認必須 + デフォルト OFF** | |
| 避難所への到着確定 | 自動(ジオフェンス)or 本人 | 誤検知時は本人が取り消し可 |

### 6.5 SafetyValidator(ハードルール)

```
reject if shelter.floodDepthClass >= 2  when disasterType in [heavy_rain, flood]
reject if shelter.tsunami == false      when disasterType == tsunami
reject if hazardCell(route).landslide   when disasterType in [heavy_rain, earthquake]
reject if crowd.assigned >= capacity
reject if walkMin > 40 (別候補があれば)
reject if shelter.types に disasterType 対応種別が無い
```
NG 時は `rejectedCandidates` に理由付きで記録 → Agent Log に「AI は A を選んだが浸水想定 2m のため却下、B に再選定」と表示。これが③のハイライト。

### 6.6 フォールバック(ルールベース)

LLM が 3 回失敗 / 8 秒タイムアウト / JSON 破損 → `score = 種別適合(必須) + 距離 + (1-crowd) + 標高(水害時)` で決定的に選定。`validatedBy: "fallback"` を付け、UI に「AI 応答なし・安全ルールで選定」と明示。**案内は絶対に止めない**。

### 6.7 モデル選択とコスト

| ステップ | モデル層 | 理由 |
|---|---|---|
| 関連判定 | 小型(OrcaRouter で cheap tier 指定) | 全ユーザーに毎回走る |
| 避難要否+選定 | 上位 | 命に関わる判断、1 インシデント 1〜2 回 |
| 再選定 | 中型 or ルールのみ | 満員切替は候補差し替えのみで LLM 不要にできる |
| 経路 | LLM 不使用 | |
| 理由文の整形 | 上位の出力をそのまま(追加呼び出しなし) | |

Agent Log に各呼び出しの model / tokens / usd を出し、インシデント合計を表示。ピッチで「1 インシデント約 $0.0X、待機中 0」。

## 7. OrcaRouter 連携(公式ドキュメント確認済 2026-09-20)

**予算**: スポンサー付与 ¥3,000 分。1 インシデント数円想定なので開発含め余裕あり。ただし tool calling ループの暴走(無限ループ)だけはガードする(§7.4)。

### 7.1 基本
- Base URL: `https://api.orcarouter.ai/v1`、OpenAI SDK 互換(Node の `openai` パッケージをそのまま使用)
- 認証: `Authorization: Bearer sk-orca-...` → **Firebase Functions の Secret に保管、端末には絶対に置かない**
- モデル ID は `provider/model` 形式。`GET /v1/models` で利用可能一覧を取得
- tool calling: OpenAI 形式 `tools` / `tool_choice` が全プロバイダで動作(Anthropic/Gemini へは自動変換)。**ツール名は `googleSearch` `codeExecution` `urlContext` を避ける**(Gemini 予約名)
- structured outputs: `response_format: json_schema` は OpenAI / Gemini 系のみ。Anthropic 系は非対応 → **本アプリでは最終出力も tool(`submit_decision`)で受ける**ことで全プロバイダ共通にする
- ZDR がデフォルト: プロンプト・出力・ツール引数はゲートウェイに保存されない(メタデータのみ 13 か月)。※上流プロバイダの保持は別 → ピッチではこの但し書きも正直に言う

### 7.2 モデル戦略(②コスパ)
Named Router をコンソールで 2 つ作る(`model: "orcarouter/{name}"` で呼ぶ):

| ルータ名 | 用途 | Strategy | Allowed models(例) |
|---|---|---|---|
| `evac-triage` | 関連判定(毎回・全員に走る) | `cheapest` | `openai/gpt-4o-mini, google/gemini-2.5-flash-lite` |
| `evac-decide` | 避難要否・避難所選定 | `quality` or `balanced` | 上位モデル群(利用可能なものから) |

- 選定の再実行(満員切替)は LLM を呼ばず候補差し替えのみ → トークン 0
- 障害フォールバック: `extra_body: { route: "fallback", models: ["...", "..."] }`(最大 5、5xx/429/ネットワークエラー時のみ発火)。**これは品質昇格ではなく可用性の話**としてピッチする
- 時間が無ければ Named Router を作らず、直接モデル ID を tier 定数で指定しても可(挙動は同じ、見栄えが少し落ちるだけ)

### 7.3 使用モデル・コストの取得(Agent Log 用)
- 全リクエストにヘッダ `X-OrcaRouter-Include-Cost: true` → レスポンス `usage.cost_usd`(USD)
- レスポンスヘッダを保存: `X-Orca-Resolved-Model`(実際のモデル)/ `X-Orca-Router` / `X-Orca-Fallback-Level` / `X-Orca-Fallback-Model` / `X-Orca-Request-Id`
- 確定値が要るときは `GET /v1/generation?id={X-Orca-Request-Id}` → `data.total_cost`
- Node SDK では `client.chat.completions.create(...).withResponse()` でヘッダにアクセス

### 7.4 tool calling ループの実装方針
- LLM に公開するツール: `get_hazard(area_cell)`, `list_shelters(disaster_type)`, `get_crowd(candidate_ids)`, `submit_decision({choice, should_evacuate, reasons, confidence})`
- 引数・戻り値はすべて抽象化済み(§6.3)。座標・実名は Functions 内のマップで仮名 ↔ 実体を変換
- 最大 6 ターン / 全体 8 秒でループ打ち切り → 未呼び出しの必須ツールはシステムが補完 → それでも `submit_decision` が無ければフォールバック
- Agent Log には「LLM が選んだツール」「システムが補完したツール」を区別して記録

### 7.5 Guardrails(①のデモ)
- コンソール `/console/guardrails` で `type: pii`, `stage: input`, `action: mask`, `entities: ["email","phone","credit_card"]` を作成 → デモ用 API キーにアタッチ
- 挙動: `jane@acme.com` → `[EMAIL]` に置換して上流へ。block 設定時は HTTP 400 `guardrail_blocked`(課金なし)
- **注意**: 組み込みエンティティに「氏名」「住所」「座標」は無い(email/phone/credit_card/ssn/ip/api key 等のみ)。→ 位置・氏名を守るのは**アプリ側のデータ最小化(§6.3)が主役**で、Guardrail は自由文送信(§6.4 承認必須の操作)にメール・電話が混じった時の防波堤、という位置づけがドキュメント的にも正しい。ピッチでもそう言う
- デモ: 承認カードから「連絡先 090-xxxx に伝えて」と自由文を送る → LLM 整形時に `[PHONE]` に置換されたことを Matches タブとログで見せる

### 7.6 Agent Firewall(余裕があれば・①④の加点)
- ワークスペースの Firewall ルールで `stage: response`, `tool_name_glob: "send_*"`, `verdict: pending_approval` のようにすると、LLM が通知送信ツールを呼んだ時に HTTP 400 `firewall_approval_pending` + approval ID が返り、承認後に `X-OrcaRouter-Firewall-Approval` ヘッダで再送できる
- 本アプリの承認カード(§6.4)をこの仕組みに載せると「承認ゲートがアプリ実装でなくゲートウェイ層で強制されている」と言えて強い。ただし実装コストと不確実性があるので **Phase1 はアプリ側実装、Firewall は"本番ではこう載せる"としてスライド 1 枚**

### 7.7 疎通確認タスク(最初の 30 分)
1. `curl /v1/models` で利用可能モデルを確認し、triage/decide の候補を決める
2. `X-OrcaRouter-Include-Cost: true` 付きで 1 リクエスト → `usage.cost_usd` と `X-Orca-Resolved-Model` が取れることを確認
3. tools 付きリクエストで `tool_calls` が返ることを確認(Anthropic 系モデルでも)
4. Named Router 2 つ作成 → `orcarouter/evac-triage` で呼べることを確認

## 9. デモシナリオ(発表用・約 4 分)

1. **平時**: 出張先(デモ地域)で Home を開く。周辺避難所とハザードが出る。「ここまでは普通の防災アプリ」
2. **発火**: 管理画面から「震度 6 弱・地震」発火 → 別端末/モックの全員に通知
3. **自律**: 通知を開く → 2〜3 秒で「◯◯小学校へ、徒歩 8 分。理由: 広域避難場所 / 浸水域外 / 混雑 30%」。同時に Friends 画面(別端末)で自分が「避難中・◯◯小学校」に変わる。「私は何も押していません」
4. **群制御**: 管理画面で ◯◯小学校を満員に → 自動で次点へ切替、フレンドにも行き先変更が届く
5. **判断が変わる**: 「同じ場所で豪雨だったら」発火 → 高所の別避難所へ。「災害種別で判断が変わる」
6. **裏側(①②③)**: AgentLog を開く。LLM に渡した入力に座標が無い / A を選んだが浸水想定で却下→B / 使用モデルとコスト合計 / (可能なら)LLM を落として案内が止まらない
7. **終了**: 到着 → 「避難完了」→ フレンドに届く → エージェント停止・記録

## 14. デモモード仕様

### 14.1 入り方

### 14.2 デモ操作パネル(管理画面 or Settings 内)
| 操作 | 内部動作 |
|---|---|
| 地震(震度 6 弱)発火 | `alerts/` に `{type:"earthquake", source:"demo", maxInt:"6-", epicenter:デモ地点付近, affectedAreaCodes:[デモ地域]}` |

| LLM 障害を注入 | `runAgent` に `demo.failLlm=true` → OrcaRouter 呼び出し前に強制エラー → フォールバック経路を実演 |
| フレンドの状態を進める | モックフレンドの statuses を evacuating→arrived に更新 |
| リセット | デモ incident・crowd・statuses を初期化 |

- 未確定(要決定)。候補: 東京都心の河川近く(荒川/隅田川沿い。浸水想定が濃く、豪雨で判断が変わりやすい)、かつ高台の避難所も徒歩圏にある場所。例: 墨田区・江東区・北区赤羽 など。→ 決めたらその周辺の skhb タイルを事前キャッシュ

| 地震検知 | **P2P地震情報 API v2** `https://api.p2pquake.net/v2/history?codes=551,556&limit=5` | Functions(2 分ポーリング) | 緯度経度が数値。`scale` 10=震度1…45=5弱, 50=5強, 55=6弱, 60=6強, 70=7。IP あたりレート制限あり → サーバー 1 箇所から。バックアップ: JMA `https://www.jma.go.jp/bosai/quake/data/list.json` |
| 大雨/洪水/土砂/津波 警報 | **JMA** `https://www.jma.go.jp/bosai/warning/data/warning/map.json`(全国) | Functions(2 分ポーリング) | `areaTypes[1].areas[].code`(市区町村 7 桁)+ `warnings[].code`(03 大雨警報 / 04 洪水警報 / 33 大雨特別警報 等、コード表は自前定数)。非公式 API |
| 現在地→市区町村コード | GSI 逆ジオコーダ `https://mreversegeocoder.gsi.go.jp/reverse-geocoder/LonLatToAddress?lon=&lat=` | Functions | `muniCd`(5 桁)→ JMA class20 は `muniCd + "00"` |
| 浸水・土砂・津波リスク判定 | **ハザードマップポータル タイル** `https://disaportaldata.gsi.go.jp/raster/{layer}/{z}/{x}/{y}.png` layer: `01_flood_l2_shinsuishin_data`(洪水 想定最大)/ `04_tsunami_newlegend_data`(津波)/ `05_dosekiryukeikaikuiki`・`05_kyukeishakeikaikuiki`(土砂) | Functions(z16 タイル取得 → `pngjs` でピクセル色 → 浸水深クラス)。表示は Flutter 側で TileOverlay | 洪水凡例色: 0.5m未満 `#F7F5A9` / 0.5–3m `#FFD8C0` / 3–5m `#FFB7B7` / 5–10m `#FF9191` / 10–20m `#F285C9` / 20m〜 `#DC7ADC`(要実機確認)。出典表記必須 |
| 避難所候補 | **GSI 指定緊急避難場所 GeoJSON タイル** `https://cyberjapandata.gsi.go.jp/xyz/skhb0{N}/10/{x}/{y}.geojson` N: 01 洪水 / 02 崖崩れ・土石流 / 03 高潮 / 04 地震 / 05 津波 / 06 大規模火事 / 07 内水氾濫 / 08 火山 | Functions(z10 タイル 1〜4 枚 → 距離順)。結果を Firestore にキャッシュ | **災害種別ごとにタイルが分かれている = 種別適合フィルタがデータ側で済む**。属性: `name`, `address`, `remarks`。収容人数は無い → 混雑カウンタの capacity はデモ用に仮値(例 300) |
| 標高 | GSI `https://cyberjapandata2.gsi.go.jp/general/dem/scripts/getelevation.php?lon=&lat=&outtype=JSON` | Functions(候補ごと、キャッシュ) | `{"elevation":30.4}`。範囲外は `"-----"` 文字列 |
| 経路 | Google Directions API(mode=walking) | Functions | polyline のみ端末へ。キー無しなら直線+徒歩分(80m/分)で代替 |
| 雨量(平時表示・任意) | JMA アメダス `https://www.jma.go.jp/bosai/amedas/data/map/{yyyyMMddHHmm00}.json` | Functions | Phase2 でよい |

### 15.1 ツール実装メモ(functions/src/agent/tools/)
- `getAreaCode(lat,lng)` → GSI 逆ジオ → `{muniCd, name}`
- `getHazard(lat,lng)` → 3 レイヤのタイルを並列取得 → `{flood: 0..5, tsunami: bool, landslide: bool}`(z16、`pngjs`)
- `listShelters(lat,lng,disasterType,radiusM)` → 該当 skhb タイル取得 → haversine 距離 → 上位 8 件 → 各件 `getElevation` + `getHazard`(候補地点)+ crowd を付与 → 仮名 A..H を振る
- `getRoute(from,to)` → Directions → `{polyline, distanceM, durationS}`
- `getCrowd(ids)` → Firestore
- 抽象化: LLM に渡す前に `{id:"A", walkMin:8, kinds:["earthquake","flood"], elevationM:12, hazard:{flood:0,...}, crowdPct:30}` に変換。座標・実名は Functions 内 Map に保持

## 16. ブランド・UI 決定事項(2026-09-20 master 決定)

- **アプリ名**: ヒナミチ(HINAMICHI)/ タグライン「もしもの時に、迷わないための"わたしの道しるべ"」「大切な人と、帰るための道を。」
- **キャラクター**: セナヴィ(SENAvi, Safety Navigator AI)= 白い子犬。**エージェントそのものの擬人化**。
- **セナヴィの表情 = エージェント状態**(§6.1 と対応させる):
  | incident.state | セナヴィ | 画面上の一言 |
  |---|---|---|
  | IDLE | いつもそばに(通常) | 「今日は◯◯です。お出かけ気をつけて」 |
  | ASSESSING_RELEVANCE / DECIDING | 状況を確認中(真剣) | 「ちょっと待ってね、確認してる」 |
  | GUIDING / RESELECTING | 一緒に避難(真剣→安心) | 「◯◯小学校へ。徒歩8分。一緒に行こう」 |
  | ARRIVED / SAFE_ZONE | 到着をお知らせ(にっこり) | 「無事に着いたよ。みんなに伝えたよ」 |
  | FALLBACK_GUIDING | 真剣(変えない) | 「AIの返事が遅いから、安全ルールで決めたよ」 |
- **トーン**: やさしい・あたたかい(ベージュ/サンド基調)。警告色は赤 `#E57373`/アンバー `#F5C368` を最小面積で。成功は `#7CB342`
- **パレット**: 2 案あるので統一が必要(A: `#F7E7D9/#E9C9A8/#D4A574/#A7B8A0`、B: `#F5F6F8/#E5E0D8/#F5C368/#E57373/#7CB342`)。→ 推奨 **B をベース色に、A のオレンジベージュをキャラ周りのアクセントに**。理由: 屋外・直射日光での可読性と、緊急/成功の色差が B の方が確保できる
- **フォント**: Noto Sans JP(見出し Bold / 本文 Regular)
- **画面フロー(デザイン側)**: 01 スプラッシュ → 02 ホーム(平時) → 03 災害発生時 → 04 避難経路の案内 → 05 避難先の詳細 → 06 避難完了、他に 防災情報一覧 / 設定
- **設計側で追加が必要な画面**: Friends(見守り・安否状態)/ AgentLog(AI の判断記録)/ Approval(承認カード)。Friends はデザイン A 面の「家族・友人の安否確認」モックがあるので流用可
- **03 画面の扱い(master 決定 2026-09-20)**: 通知を開いた時点で AI の判断は**完了済み**。03 には「避難が必要です」+ 行き先・徒歩分・理由 3 点がすでに表示されている。ボタンは「このルートで行く」= **人の承認**(AI の起動ではない)。押すと status=evacuating と行き先がフレンドへ共有され、ナビ開始
  - **無応答タイムアウト**: 30 秒(調整可)操作がなければ自動でナビ開始、フレンドには「応答なし・◯◯へ誘導中」を送る(パニック・負傷で操作できない人を想定)
  - 「あとで確認」を選んでも、警報格上げ・浸水想定域内など状況悪化時は AI が再度割り込む
  - 満員・通行止めによる経路切替は承認なしで自動(「行く」と決めた範囲内の変更)
  - ピッチの一言:「判断はすべて AI、実行の入り口だけ人。人が動けなければ AI が進める」
  - §6.4 権限モデルに「ナビ開始 = 承認 or 30 秒タイムアウトで自動」を追記
- **スコープ外(Phase2)**: 音声案内(デザインに記載あり)、ログイン(匿名認証で省略)、トークルームの既読表示(§3 Phase 2)

### 17.4 セナヴィの状態マッピング(`lib/domain/senavi_mood.dart`)

enum SenaviMood { normal, serious, surprised, smile, troubled, lying, running, lookback }

SenaviMood moodFor(IncidentState s) => switch (s) {
  IncidentState.idle => SenaviMood.normal,
  IncidentState.assessing || IncidentState.deciding => SenaviMood.serious,
  IncidentState.proposing => SenaviMood.serious,      // 03 画面
  IncidentState.guiding => SenaviMood.running,
  IncidentState.reselecting => SenaviMood.surprised,   // 1.5 秒後 serious へ
  IncidentState.arrived || IncidentState.safeZone => SenaviMood.smile,
  IncidentState.notRelevant || IncidentState.monitoringStay => SenaviMood.normal,
  IncidentState.fallbackGuiding => SenaviMood.serious,
  IncidentState.offline => SenaviMood.troubled,
};

String lineFor(IncidentState s, {String? shelter, int? walkMin, String? weather}) => switch (s) {
  IncidentState.idle => '今日は$weatherです。お出かけ気をつけて',
  IncidentState.assessing || IncidentState.deciding => 'ちょっと待ってね、確認してる',
  IncidentState.proposing => '$shelterへ。徒歩$walkMin分。一緒に行こう',
  IncidentState.guiding => 'あと$walkMin分。このまま進もう',
  IncidentState.reselecting => 'あっちは混んでる。こっちに変えるね',
  IncidentState.arrived || IncidentState.safeZone => '無事に着いたよ。みんなに伝えたよ',
  IncidentState.notRelevant => '今回は大丈夫。念のため様子を見てるね',
  IncidentState.monitoringStay => '今は動かない方が安全。ここで待とう',
  IncidentState.fallbackGuiding => '返事が遅いから、安全ルールで決めたよ',
  IncidentState.offline => '電波が弱いみたい。最後に決めた道を進もう',
};

### 18.1 `orca.ts` の呼び出し規約(実装用)

```ts
// functions/src/agent/orca.ts
import OpenAI from "openai";
const client = new OpenAI({ baseURL: "https://api.orcarouter.ai/v1", apiKey: ORCA_KEY });

type Tier = "triage" | "decide";
const ROUTER: Record<Tier, string> = { triage: "orcarouter/hina-triage", decide: "orcarouter/hina-decide" };
const FALLBACK: Record<Tier, string[]> = {
  triage: ["openai/gpt-4o-mini", "google/gemini-2.5-flash-lite", "deepseek/deepseek-chat"],
  decide: ["anthropic/claude-sonnet-4.5", "openai/gpt-4o", "google/gemini-2.5-pro"],   // /v1/models で実在確認して差し替え
};

export async function chat(opts: {
  tier: Tier; incidentId: string; promptRef: { name: string; variables: Record<string, unknown> };
  messages: OpenAI.ChatCompletionMessageParam[]; tools?: OpenAI.ChatCompletionTool[];
  escalateOnce?: boolean; demoFail?: boolean;
}) {
  if (opts.demoFail) throw new Error("demo: forced LLM failure");
  const { data, response } = await client.chat.completions.create({
    model: ROUTER[opts.tier],
    messages: opts.messages,
    tools: opts.tools,
    // @ts-expect-error OrcaRouter 拡張
    prompt_ref: { name: opts.promptRef.name, label: "production", variables: opts.promptRef.variables },
    extra_body: { route: "fallback", models: FALLBACK[opts.tier] },
  }, {
    headers: {
      "X-OrcaRouter-Include-Cost": "true",
      "X-OrcaRouter-Session-Id": opts.incidentId,
      ...(opts.escalateOnce ? { "X-OrcaRouter-Escalate": "once" } : {}),
    },
    timeout: 8000,
  }).withResponse();

  const h = (k: string) => response.headers.get(k) ?? undefined;
  return {
    data,
    meta: {
      requestId: h("x-orca-request-id"), router: h("x-orca-router"), resolvedModel: h("x-orca-resolved-model"),
      fallbackLevel: Number(h("x-orca-fallback-level") ?? 0), fallbackModel: h("x-orca-fallback-model"),
      sessionTier: h("x-orca-session-tier"), prompt: h("x-orca-prompt"),
      costUsd: (data.usage as any)?.cost_usd as number | undefined,
    },
  };
}
```
`meta` はそのまま `agentLog` に書く。Agent Log 画面の「審査員向け」タブはこの `meta` を表示する。

## 19. 実機・デモ地点の確定(2026-09-20)

### 19.1 実機
- iPhone と Android の両方あり。**役割を分ける**:
  - **Android = 本人(被災者)端末・主デモ機**。理由: FCM プッシュが追加費用なしで即動く
  - **iPhone = フレンド(見守り)端末**。Friends 画面は Firestore のリアルタイム購読で動くのでプッシュ不要
- ⚠️ iOS でプッシュ通知を受けるには **Apple Developer Program(有料・年 ¥12,800 前後)+ APNs キー**が必要。未加入なら iOS はプッシュ無しで運用(アプリを開いていれば Firestore 経由で同じ体験になる)。加入済みなら両方でプッシュ可
- iOS の位置情報は **「常に許可」が要る**(§5.1 の位置共有をオンにする場合)。`UIBackgroundModes: location` を Info.plist に入れてある。共有をオフで運用するなら「使用中のみ」で足りる
  - 許可が取れなかったらスイッチを戻す実装にしてある(オンに見えて送っていない、という嘘の状態を作らない)
- 会場では Wi-Fi が不安定なことが多い → **両端末ともモバイル回線で動作確認**しておく

### 19.2 デモ地点 = 千葉県市川市南行徳
- 選定理由がそのまま説明になる: 江戸川・旧江戸川と東京湾に挟まれた**海抜ゼロメートル地帯**。洪水(江戸川氾濫時 3〜5m 浸水想定)・高潮・津波・液状化のリスクが全部あり、**地震(広域避難場所)と豪雨(浸水想定外の高所・上層階)で行き先が変わる**ことを実データで示せる
- 事前確認タスク(Day1): 南行徳駅周辺で `skhb01(洪水)` `skhb04(地震)` `skhb05(津波)` の GeoJSON タイルを取得し、候補が種別ごとに違う顔ぶれになることを確認。ならない場合は半径を調整
- ハザードタイルの z16 を南行徳周辺で事前取得し、色→浸水深クラスの変換が想定通りか目視確認(凡例色は要実機確認と §15 に記載)

### 19.3 「発表当日、会場の現地で本当に動く」ための設計
発表会場は南行徳ではない(はず)。**デモは会場の実際の GPS 位置で動かす**前提にする。

- **デモ発火は「この端末の現在地」を基準にする**。`demoFire` は `alerts/` に書くとき、影響エリアを固定の市区町村コードにせず、**発火した端末の現在地から逆ジオで求めた市区町村コード**(+隣接)を `areaCodes` に入れる。震源座標も現在地から数 km ずらした点を生成。→ 南行徳でも会場でも自宅でも、同じ操作で「自分に関係ある災害」として成立する
- 位置オーバーライド(§14.1)は**リハーサル用**に残す(自宅から南行徳を再現するため)。当日は OFF
- 会場が屋内で GPS が取れない場合に備え、**「最後に取得できた位置」を 10 分保持**し、それでも無ければ位置オーバーライドに自動フォールバック(Settings の既定オーバーライド地点 = 南行徳)。Agent Log に「位置: 実 GPS / 保持値 / オーバーライド」を明記して正直に見せる
- 避難所・ハザード・標高・経路は**会場周辺でも全部実 API で取れる**(全国データ)。ただし当日の通信断に備え、**会場周辺のタイルと避難所候補を前日に取得して Firestore にキャッシュ**しておく(キャッシュがあれば API が落ちても動く = ③の話にもなる)
- **会場の住所が分かり次第**、前日リハで「会場の位置で地震/豪雨を発火 → 行き先が変わる → 満員切替 → 到着」を通す。会場の候補避難所に「学校名」など発表で映えるものがあるかも確認
- 発表中に本物の警報が出た場合は、デモより優先して本物で動く(§14.4)。むしろ最高の証拠になる

## 20. 「課金なし」制約による構成変更(2026-09-20・§4 §12 §15 §19.4 を上書き)

**制約**: クレジットカード登録を含む課金は一切しない。これにより以下 3 つが使えない。
- Firebase **Cloud Functions**(Blaze プラン=カード登録必須)
- **Google Maps Platform**(課金アカウント必須)
- **Apple Developer Program**(iOS プッシュ・配布)

代替は全部「カード不要の無料枠」で組む。**エージェント設計・データモデル・UI は一切変わらない**。変わるのは "どこで動くか" と "地図の描き方" だけ。

- プッシュ通知は不可 → iPhone は**フレンド見守り端末**。Friends 画面は Firestore 購読なので体験は同じ。本人端末は Android
- 万一 Android 側で問題が出た場合の保険として、iOS でも「アプリを開いた状態で `alerts` を購読 → 端末内ローカル通知を出す」経路を用意(flutter_local_notifications はプッシュ不要で動く)
